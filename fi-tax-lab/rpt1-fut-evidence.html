ที่มาของสองโลก: post เข้า GL ใช้ rate M @ T (หลักบัญชี ค่ากลาง ณ วันเกิดรายการ) · แต่เกณฑ์สรรพากรไทยใช้ rate BOT วันทำการก่อนหน้า (T-1 ≈ เลน B) — ช่องว่าง M@T ↔ B@T-1 คือเหตุผลการมีอยู่ของ TAX-ENH-2 (post ส่วนต่างปรับ WHT) และการที่ RPT-1 ต้องโชว์ 2 FX column เทียบกัน

ชื่อ misleading: “Fx on posting date” จริง ๆ คือ rate ของ วันก่อนหน้า posting date (BUDAT−1) ไม่ใช่วัน posting เอง
กติกาสื่อสารเด็ดขาด: ห้ามพูด “T-1” กับ GL team — fix target ของเขาคือฝั่ง TaxPmt เท่านั้น · ประโยคเดียวที่ใช้: “bank line must use the payment document’s date” · เผลอพูด T-1 ปน = เสี่ยง GL แก้ขา bank ไปใช้ T-1 → ผิดบัญชี + defect ใหม่ซ้อน

1.4 กลไกเลือก + เย็บเอกสาร Confirmed

รายงาน เกาะเส้น WHT ที่จุดจ่าย (ACDOCA KTOSL='WIT') เป็นสมอ · VAT36 เป็นผู้โดยสาร:

  • มี WHT + มี VAT36 → โผล่ครบทุก column
  • มี WHT ไม่มี VAT36 → ยังโผล่ · ฝั่ง VAT36 ว่างโดย design (= สาระ TC-008)
  • มี VAT36 ไม่มี WHT → ไม่โผล่เลย (= สาระ TC-009 + ใบ control)

1 แถว = เย็บสูงสุด 4 ใบ: (1) Invoice จาก FB60 → base, VAT36 lines, invoice currency, PC/RI · (2) Payment จาก F-53 → WHT line, KURSF, วัน T · (3) VAT36 doc 9xxxxxxxxx ที่ ZTAXA_R02 สร้าง · (4) WHT FX adj doc (type SW) ที่ ZTAXA_R03 สร้าง · ตัวเย็บ = clearing (BSAK/BSEG-AUGBL) ที่เกิดตอน activate open item ใน F-53

Precision ที่มักสลับ: ช่อง Document Number บน selection รับเลข “Invoice” (AP Voucher) ไม่ใช่เลข payment · selection กรองที่จุดตั้งต้นฝั่ง invoice แล้วโปรแกรมไต่ clearing ไปหา payment เอง (FD 19/27) · “พร้อมกัน” = “ถูกเย็บถึงกันแล้ว ณ วัน run” · invoice ที่ยังไม่จ่าย = ไม่โผล่ (ภาระเกิด ณ จุดเงินออก)

1.5 Execution chain = read-only Confirmed

ลำดับ business: (01) AP posting → (02) ZTAXA_R03/TAX-ENH-2 → (03) ZTAXA_R02/TAX-ENH-3 → (04) RPT-1 · ประโยค KT sheet (“report generated after E032 & E040”) = ลำดับงาน user สิ้นเดือน ไม่ใช่เงื่อนไขทางเทคนิค

ข้อเท็จจริงสำคัญ: RPT-1 read-only · run ได้เสมอ ไม่ error ไม่ block — chain กระทบแค่ 2 column: “Doc WHT FX Adj” ว่างจนกว่า E032 run · “VAT36 Doc No.” ว่างจนกว่า E040 run · ที่เหลือ (WHT amounts, 2 FX columns, VAT36 base/amt FC, PC, RI) มาจาก doc + logic เอง
→ กฎออกแบบ TC ข้อเดียว: run chain เฉพาะเมื่อ column ที่ TC ตรวจต้องพึ่งมัน
Open VAT36 base/amt (FC) น่าจะขึ้นจากฝั่ง invoice โดยไม่รอ R030 — แต่ยังไม่ verify ด้วยตาบน doc ที่ R030 ยังไม่แตะ · TC-007 step 3 (baseline) คือการทดลองที่จะตอบ

1.6 ระบบ rate: เลน · valid-from · ความเสี่ยงวันจันทร์ Confirmed ครึ่ง

OB08/TCURR เก็บแบบ valid-from (แต่ละบรรทัดมีผล “ตั้งแต่วันนั้นจนกว่าจะมีบรรทัดใหม่”) · standard หา rate ด้วย ล่าสุดที่ ≤ วัน posting · เสาร์อาทิตย์/วันหยุดไม่มี rate ใหม่ → ใช้บรรทัดวันทำการล่าสุด (พิสูจน์แล้ว: จ่ายอาทิตย์ 02.08 ระบบดึง 32.57230 ของศุกร์ 31.07)

Rate type = เลนขนานในตารางเดียว: M=middle (post FI ถูกล็อคเลนนี้) · B=selling (≈BOT ฝั่งขาย) · G=buying · custom ZTH (TAX-ENH-2 ฝั่ง LC3) / ZOM (RPT-2 Oman)

Open — KT ข้อ 3 ความเสี่ยงวันจันทร์: FD step 28 เขียน lookup GDATU=BUDAT−1 · ถ้า Z-code เขียน exact match แทน ≤ fallback → payment วันจันทร์/หลังวันหยุดจะได้ Fx on posting date = blank (BUDAT−1=อาทิตย์ ไม่มี GDATU) · อาการเหมือน TC-003 แต่คนละเหตุ · พิสูจน์ฟรีด้วย “การทดลองวันจันทร์” · ฝั่ง GL posting พิสูจน์แล้วว่าใช้ ≤ · เหลือฝั่ง report

TKT-02Exchange rate at payment (ขา bank ใน GL)

Scope ยืนยัน: เกิดเฉพาะ currency case 1 (invoice สกุลที่สาม GBP/EUR → payment USD) และเฉพาะ payment ที่ มี WHT line · case 2 (USD→THB) / case 3 (THB invoice) ไม่โดน · root cause อยู่ ฝั่ง posting ไม่ใช่รายงาน — RPT-1 เป็นกระจก read-only

Owner: fix = GL team · config = Config owner · comms routing = Comms lead · Acceptance criterion: bank outgoing line converts at the payment document’s date

Controlled experiment (02.08) — คู่แฝดต่างตัวแปรเดียว

เงื่อนไข: rate M USD→THB วัน invoice (24.07 = 32.34140) ต้องต่างจากวันจ่าย (02.08 = 32.57230), delta = 0.23090 · ถ้า rate 2 วันเท่ากัน bug ล่องหน (บทเรียนเดียวกับ F6 ของ RPT-2 ที่ flat rate ใน DEV บังไว้)

ใบ 8084322444 (ของทีม, จ่าย 14.07) + correction

Correction ระหว่างวิเคราะห์สด เคยสรุปว่า “ใบ 457 ขา bank/WHT ใช้ rate ผิดวัน (32.588 แทน 32.637)” — อ่านผิด เพราะอ่านตาราง OB08 คลาดบรรทัด: rate M USD→THB มีผล 14.07 คือ 32.58770 ไม่ใช่ 32.637 · ดังนั้นขา bank (37,530.28÷1,151.67=32.588) และ WHT (6,622.95÷203.23=32.589) ของใบ 457 แปลง USD→THB ที่ rate วันจ่ายถูกต้อง

ความผิดปกติของ 457 อยู่คนละจุด: การแปลง GBP→USD (vendor 1,354.90 / bank net 1,151.67) ใช้ cross rate ของ 07.07 ทั้งที่จ่าย 14.07 · สอดคล้องกลไกกับ 502: ทั้งคู่ยอดถูก derive จากมูลค่า ณ วันเก่า แทนแปลงจริง ณ วันจ่าย — แค่คนละมิติ (457 เพี้ยนเลน USD, 502 เพี้ยนเลน THB) · การ map กลไกต่อใบเป็นงาน triage ของ GL team · หน้าที่เรา = ส่งเลข observed ครบ

  • จำนวนบรรทัดไม่ fix — RealizedFX แตก 2 บรรทัดใน 502 (THB 6,173.21 / group 15.24-) เพราะแต่ละเลนสกุลเพี้ยนไม่เท่ากัน · เทียบ doc ให้เทียบ โครงหน้าที่ ไม่ใช่นับแถว
  • ขยะจาก bug (FX lines) ลง PC C_PC11 / RI CP — ไหลเข้า profit center เดียวกับที่ RPT-1 และ TC-005 answer key อ่าน = เหตุผลต้องแก้ที่ posting ไม่ใช่ปัดที่รายงาน

3.3 ทักษะ SAP จากการลงมือจริง

FB60 (Invoice) — 6 จุดที่ต้องรู้
  • Branch Code = สาขาสรรพากรของ ผู้ขาย (คนละช่องกับ Bus.Place=สาขาเรา) · บังคับเฉพาะ vendor ไทย · validate กับ branch data ใน BP master (F4 ว่าง = master ไม่มี พิมพ์เองไม่ผ่าน) · foreign vendor ไม่โดน — พอดี scenario ภงด.54/ภพ.36 (จ่ายต่างประเทศ)
  • rate เกาะ Posting Date ไม่ใช่ Invoice date — backdate ต้องเปลี่ยนทั้งคู่
  • tab Withholding tax ต้องแวะดูก่อน Post เสมอ (ถ้าว่างระบบไม่เตือน post ผ่านเงียบ ๆ → doc ใช้กับ RPT-1 ไม่ได้)
  • cost object บน expense line = ตัวกำหนด PC/RI ในรายงาน (chain: Cost Center → Profit Center → Segment) · warning “segment invalid” = ยังไม่ใส่ cost assignment
  • หลักเลือก master data: “doc ใหม่ บน master data ที่ proven” — ลอก vendor/tax code/G-L/cost center จาก doc ที่ผ่าน chain มาแล้ว (FB03) แทนสุ่ม
  • tax code: V1/V2 = 7% ClaimPP36 (ยึด label ในระบบ)
F-53 (Payment) — Assigned loop + จุดพลาด
  • ขา bank เกิดจาก header เท่านั้น — Bank data ว่าง = doc ไม่มีขาเงินออก (overview โชว์ 0 line / INTERNAL)
  • ช่อง Currency default THB ต้องเปลี่ยนก่อนทำอย่างอื่น · ยอดจ่าย = net หลังหัก WHT ไม่ใช่ยอดเต็ม
  • เทคนิค Assigned loop: ใส่ยอดประมาณ → Process Open Items → อ่านค่า Assigned (=ยอดเป๊ะที่ระบบต้องการ) → back → แก้ Amount → Not Assigned = 0.00
  • activate เฉพาะใบเป้าหมาย (vendor test มี open items ปนหลายใบ) · CashDiscount ปล่อยว่างเสมอ
  • อ่านจอ: Assigned ÷ Gross = 0.85 → WHT 15% ทำงาน โดยไม่ต้องเปิด tab · tab WH Tax = จุด capture evidence ว่า payment มี WHT line
FB03 (Display) — posting keys + implied rate
  • posting keys: 31 เครดิตเจ้าหนี้ / 25 เดบิตล้างเจ้าหนี้ / 40-50 เดบิต-เครดิต G/L · vendor line โชว์ reconciliation account ไม่ใช่ expense
  • LC Amount (THB) = เลนที่รายงานภาษีไทยอ่าน · Group Curr (USD) = LC2 เพื่อ consolidation อ่านข้ามได้
  • เทคนิค implied rate: LC ÷ Amount ของแต่ละบรรทัด บอกทันทีว่าแปลงด้วย rate อะไร (เครื่องมือหลักที่ใช้จับ 163211)
  • Data Entry View = สิ่งที่คนกรอก · General Ledger View = สิ่งที่รายงาน/ACDOCA อ่าน (KTOSL='WIT' อยู่มุมนี้)
  • VAT36 reverse charge = ขาคู่ Def Inp VAT (สิทธิ์) + Inp VAT Pay (หน้าที่) หักล้างศูนย์ รอ R030 ประมวลสิ้นเดือน
Tax codes (client จริง): V1/V2 = 7% ClaimPP36 (สเปรดชีต config เก่าที่ว่า V2=10% outdated — ยึด label ในระบบเสมอ) · V0 ห้ามใช้แทน “ไม่มี VAT36” (ยังเป็น code กลุ่ม VAT36 อัตรา 0% → แยกไม่ออกว่า 0.00 เพราะอัตราหรือ defect) · V3–V6 unclaimable = นอก scope TC หลัก (edge case SIT + ถาม config)

Scope discipline: 1 defect 1 ticket — TC-003 blank / 163211 / GETWA dump / Monday-fallback = 4 เรื่องแยกแม้อาการคล้าย · ยำรวม = partial fix ปิด ticket แล้วเรื่องจริงหลุด
