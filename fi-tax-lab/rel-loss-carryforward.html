TAX-RPT-5 — Loss Carried Forward (ทุกประเทศ)

Type · Report Nature · New Program · ZTAXB_R03_LCF Output · FIORI custom report Complexity · Simple Priority · P1 Geo · ไทย + ต่างประเทศ

“ขาดทุนสะสมยกไป” คือสิทธิทางภาษีที่มีมูลค่าจริง — ขาดทุนปีนี้ใช้หักกำไรปีหน้าได้ ปัญหาคือ SAP มาตรฐานไม่มีที่เก็บตัวเลขนี้ RPT-5 จึงถูกสร้างขึ้นเพื่อเป็น “สมุดบัญชี LCF” ของทั้งกลุ่ม — เก็บ · แสดง · และแปลงสกุลเงินให้ SAC ใช้ต่อ Complexity = Simple แต่ criticality สูงมาก เพราะถ้าตัวเลขนี้ผิด ภาษีทุกปีถัดไปผิดหมด

Key Takeaways — 7 ข้อ
  • ข้อมูลเข้าตารางผ่าน ปุ่ม “Update table for LCF” บนหน้า output ของ current tax report — ไม่ใช่อัตโนมัติ
  • อ่านค่าจาก node “ANNUAL (PROFIT)/LOSS AFTER LCF” — เดบิต = ขาดทุน → เก็บ · เครดิต = กำไร → ไม่เก็บ
  • กดซ้ำ = เขียนทับ (overwrite) ค่าเดิม → จึงต้องเปิด change log ของตาราง
  • ZTAXB_T03 = ตารางบอกว่า “บริษัทไหนต้องแปลง LC1→LC2 ด้วย exchange rate type อะไร”
  • LC2 Conversion Balance = LC1 balance ÷ FX rate (rate สิ้นเดือนจาก TCURR)
  • IBCTC / IBCSVCS เก็บ LCF ตาม “อัตราภาษี” ไม่ใช่ตาม company-segment
  • มาเลเซียมี 2 ประเภทให้เลือก: Loss carried forward และ Unabsorbed capital allowances

ภาพรวม — ทำไมต้องมี object นี้

โจทย์

Current tax report คำนวณ “ขาดทุนคงเหลือหลังหัก LCF” ได้ทุกเดือน — แต่พอปิดปีแล้ว ตัวเลขนั้นไม่ได้ถูกเก็บไว้ที่ไหน ปีถัดไปโปรแกรมจะไม่รู้ว่ามียอดยกมาเท่าไหร่ ในโลก ECC เดิมใช้วิธี อัปโหลด flat file เข้า item type “Loss carried forward” ทุกปี = งาน manual + เสี่ยงพิมพ์ผิด

วิธีแก้ 3 ชั้น

  1. สร้างที่เก็บ — ตาราง ZTAXB_T01 เก็บ LCF ต่อ (บริษัท · ปี · งวด · profit center · segment · tax rate · TAX_INFO …)
  2. สร้างทางเข้า — ปุ่ม “Update table for LCF” บนหน้า output ของ current tax report ทั้งไทยและต่างประเทศ
  3. สร้างหน้าอ่าน — ZTAXB_R03_LCF แสดงยอด LCF ในมุมมองต่าง ๆ (รายเดือน/รายปี · สรุป/ละเอียด · LC1/2/3)

ปุ่ม “Update table for LCF” — กติกา 8 ข้อ

นี่คือส่วนที่ต้องเข้าใจแม่นที่สุด เพราะเป็นจุดที่ข้อมูลถูกเขียน

  1. ปุ่ม “Update table for LCF” ถูกเพิ่มบนหน้า output ของ current tax report ทั้งไทยและต่างประเทศ
  2. User รันรายงานตาม selection screen → รายงานแสดงผล (เช่น ตาม company code + segment)
  3. User กดปุ่มบนหน้า output
  4. โปรแกรมอ่านค่าที่ node “ANNUAL (PROFIT) / LOSS AFTER LCF” — ถ้าเป็น ยอดเครดิต = กำไร → ไม่เก็บ
  5. ถ้าเป็น ยอดเดบิต = ขาดทุนสุทธิของ company segment → เก็บลง field LCF ใน ZTAXB_T01
  6. เมื่อเก็บผลขาดทุน ผลของทุก profit center ใน company segment นั้นจะถูกเก็บด้วย ไม่ว่าแต่ละ profit center จะกำไรหรือขาดทุน
  7. ถ้ามีการปรับปรุง → กดปุ่มซ้ำ · ข้อมูลใหม่จะเขียนทับของเดิม
  8. กรณี IBCTC และ IBCSVCS → เช็คขาดทุน ตามอัตราภาษี (tax rate) · แต่ละอัตราถ้าเป็นเดบิตถือเป็นขาดทุนและเก็บ · ถ้าเครดิตถือเป็นกำไรไม่เก็บ
⚠ ข้อ 7 คือความเสี่ยงหลักของ object นี้: การเขียนทับหมายความว่า ค่าเดิมหายทันทีโดยไม่มีการยืนยัน — FD จึงสั่งไว้ตรง ๆ ว่า “Change log should be activated so that the changes made to the LCF custom table should be captured” → ตอนเทสต์ให้เช็คว่า change log เปิดจริง (ดูได้ที่ table maintenance / SCU3) ถ้าไม่เปิด จะสืบย้อนไม่ได้ว่าใครทับเมื่อไหร่
ข้อ 6 อ่านให้ดี — “ขาดทุนตัดสินที่ระดับ company segment ไม่ใช่ profit center”: ถ้า segment หนึ่งมี 3 profit center — PC1 กำไร 100 · PC2 ขาดทุน 50 · PC3 ขาดทุน 200 รวมเป็น ขาดทุนสุทธิ 150 → เก็บ LCF และ เก็บผลของทั้ง 3 profit center (ไม่ใช่เก็บเฉพาะ PC ที่ขาดทุน) เพราะทางกฎหมายภาษี หน่วยที่เสียภาษีคือนิติบุคคล ไม่ใช่ profit center · profit center เป็นเพียงมิติการบริหารภายใน

กติกา 5 ข้อ (ตรงจาก FD)

  • 1. บางบริษัทต้องแปลง LC1 → LC2 · exchange rate type ที่ใช้ถูก maintain ในตารางนี้ (เช่น บริษัทมาเลเซีย)
  • 2. เวลาแปลง LC2 → โปรแกรมเช็คตารางนี้ก่อน · ถ้ามี company code อยู่ → แปลงด้วย rate type ที่ระบุ · โดยดึง อัตราสิ้นเดือน จาก TCURR ของงวดที่รายงาน
  • 3. ถ้า ไม่มี company code ในตาราง → ไม่แปลง · ใช้ยอด LC2 เดิมจาก current tax report
  • 4. อนาคตถ้าบริษัทอื่นต้องแปลง → แค่เพิ่มบรรทัดในตารางนี้ (ไม่ต้องแก้โปรแกรม)
  • 5. ค่า LC2 conversion จะถูกใช้โดย deferred tax reporting ใน SAC
LC2 Conversion Balance = LC1 balance ÷ FX rate FX rate ← TCURR (อัตราสิ้นเดือนของงวดที่เลือกในหน้าจอ) rate type ← ZTAXB_T03-KURST ตาม company code
ทำไม “หาร” ไม่ใช่ “คูณ”: ขึ้นกับทิศทางของ exchange rate ที่ maintain ใน TCURR (from-currency / to-currency และ ratio) · FD เขียนชัดว่า “LC1 Bal divided by FX Rate” → ตอนเทสต์ต้องเช็คทั้งค่าและทิศทางด้วยการคำนวณมือ 1 บรรทัด อย่าเชื่อว่าถูกเพราะไม่ error
⚠ ทำไม Client ต้องแปลง LC1→LC2 เองแทนที่จะใช้ LC2 ที่ระบบมีอยู่แล้ว: LC2 ใน ACDOCA ถูกแปลงด้วย rate ณ วันที่ posting ของแต่ละรายการ แต่ LCF เป็น ยอดสะสม ณ สิ้นงวด — มาตรฐานบัญชี/ภาษีบางประเทศต้องการให้ตีมูลค่าด้วย อัตราสิ้นงวดเดียว ทั้งก้อน จึงต้องแปลงใหม่ · นี่คือเหตุผลที่ SAC ต้องการค่านี้สำหรับ deferred tax

Original vs Conversion vs Movement

ยอดความหมายที่มา
Original balanceยอดคงเหลือตามสกุลที่ current tax report ให้มาcurrent tax report โดยตรง
Conversion balanceยอดคงเหลือหลังแปลงด้วย month-end rateLC1 ÷ FX rate (เฉพาะบริษัทใน ZTAXB_T03)
Movementการเปลี่ยนแปลงในงวดยอดงวดนี้ − ยอดงวดก่อน

Balance includes movement + ITD (inception-to-date) จากปีก่อน — ในตัวอย่าง output ของ FD จะเห็นแถว “ITD- Dec 2023” เป็นยอดตั้งต้นของปี 2024

Expert notes

1) “Simple” ในเชิงเทคนิค ≠ “ไม่สำคัญ”

FD ให้ complexity = Simple เพราะ logic น้อย (อ่านตาราง + แปลงสกุล + แสดงผล) แต่ในเชิงธุรกิจ object นี้เป็น single source of truth ของสิทธิทางภาษี ที่มีมูลค่าเป็นตัวเงินจริง → ควรได้รับการทดสอบละเอียดกว่าที่ complexity บ่งบอก และควรมี control เรื่องสิทธิ์การกดปุ่ม Update TODO: verify ว่ามีการจำกัดสิทธิ์กดปุ่มหรือไม่ (FD ระบุ role เป็น “Display the tables and transaction”)

2) ทำไมออกแบบให้ “กดปุ่ม” แทนที่จะเก็บอัตโนมัติ

  • ข้อดี — ผู้ใช้ควบคุมได้ว่าจะยืนยันตัวเลขเมื่อไหร่ (หลังกระทบยอดเสร็จ) · รันรายงานดูเฉย ๆ ไม่ทำให้ข้อมูลเปลี่ยน
  • ข้อเสีย — ถ้าลืมกด ข้อมูลจะไม่ถูกเก็บ และปีหน้าจะไม่มียอดยกมา · เป็นความเสี่ยงเชิงกระบวนการ ไม่ใช่เชิงระบบ
  • สิ่งที่ควรทำ — ใส่ขั้นตอน “กด Update LCF” ลงใน month-end / year-end closing checklist ของทีมภาษี

3) แผนภาพความสัมพันธ์ทั้งชุด (ท่องภาพนี้ภาพเดียวพอ)

4) จุดที่ต้องตรวจเวลากระทบยอด

5 จุดตรวจ LCF รายเดือน

(1) ยอด ITD ปลายปีก่อน = ยอดตั้งต้นปีนี้ · (2) Balance = ITD ปีก่อน + ผลรวม movement ของปีนี้ · (3) LC2 Conversion = LC1 ÷ FX rate (คำนวณมือ 1 บรรทัด) · (4) บริษัทที่ไม่อยู่ใน ZTAXB_T03 ต้องไม่มีค่า conversion · (5) IBCTC/IBCSVCS — ยอดแยกตามอัตราครบทั้ง 3% และ 20%

ทวนความเข้าใจ

1. ข้อมูลเข้าตาราง LCF ได้อย่างไร และอ่านจาก node อะไร?

ผ่าน ปุ่ม “Update table for LCF” บนหน้า output ของ current tax report (ทั้ง RPT-3 และ RPT-4) · อ่านค่าจาก node “ANNUAL (PROFIT) / LOSS AFTER LCF” · เดบิต = ขาดทุน → เก็บ · เครดิต = กำไร → ไม่เก็บ

2. ZTAXB_T03 มีกี่ field และใช้ทำอะไร?

2 field — BUKRS CHAR(4) และ KURST CHAR(9) · ใช้บอกว่า บริษัทไหนต้องแปลง LC1→LC2 และใช้ exchange rate type อะไร · ถ้า company code ไม่มีในตาราง → ไม่แปลง ใช้ LC2 original

3. สูตร LC2 Conversion Balance

LC2 Conversion Balance = LC1 balance ÷ FX rate · FX rate มาจาก TCURR (อัตรา สิ้นเดือน ของงวดที่เลือก) · rate type มาจาก ZTAXB_T03-KURST

4. ทำไม IBCTC/IBCSVCS ต้องเก็บ LCF ตามอัตราภาษี?

เพราะบริษัทเดียวมีรายได้ 2 อัตรา (3% intercompany · 20% non-intercompany) ซึ่งกฎหมายให้คำนวณแยกกัน → ขาดทุนของอัตราหนึ่งใช้หักกำไรของอีกอัตราไม่ได้ จึงต้องเก็บแยก และ ZTAXB_T01 จึงมี Tax rate เป็น key

5. ถ้ากดปุ่ม Update ซ้ำ จะเกิดอะไรขึ้น และต้องป้องกันยังไง?

ข้อมูลใหม่จะเขียนทับของเดิม — FD จึงสั่งให้ เปิด change log ของตาราง เพื่อให้สืบย้อนได้ว่าใครเปลี่ยนอะไรเมื่อไหร่

6. TAX_INFO ใช้ตอนไหน ยกตัวอย่าง 2 ค่า

ใช้เมื่อ LCF มาจาก company code + profit center + segment เดียวกัน ทั้งไทยและต่างประเทศ · ตัวอย่าง: MTJDA_MY (segment MTJDA · มาเลเซีย) และ CITTH_MM · ผู้ใช้ต้องกรอกตอนรัน current tax report ต่างประเทศ ไม่งั้นค่าจะปนกัน

7. รายงานนี้มี radio button กี่กลุ่ม อะไรบ้าง และ default คืออะไร?

4 กลุ่ม — Display Currency (default LC2) · Timeperiod (default Monthly) · Type of Report (default Summary) · Malaysia Specific (default Loss carried forward)

8. ค่า LC2 conversion ถูกใช้ต่อโดยใคร?

Deferred tax reporting ใน SAC — เป็นข้อ 5 ของกติกา ZTAXB_T03 → นี่คือเหตุผลที่ต้องแปลงด้วยอัตราสิ้นงวด ไม่ใช่ใช้ LC2 ที่แปลง ณ วัน posting
