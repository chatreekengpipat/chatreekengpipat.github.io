Key Takeaways — 8 ข้อที่ตอบได้ = เข้าใจ object นี้
  • โครงข้อมูล = GL node (จาก ACDOCA) + UP node (flat file → ZTAXA_T03) + CL node (สูตร)
  • Segment เปลี่ยนชื่อ: CIT_RC→CIT_TH · PITA1→PITA1_TH · PITA3→PITA3_TH · PITA4→PSC_TH · MTJDA เท่าเดิม
  • Layout เพิ่ม BOI (ใหม่) และเปลี่ยน IHQ → IBC-TC → รวมเป็น 8 layouts
  • สูตรกลาง: ANNUAL (P/L) AFTER LCF = ANNUAL (P/L) − ALLOWANCES − LCF − LCF adjustment ใช้กับ ทุก layout
  • เลิกใช้ “Exclude profit center O*” ของ ECC — S/4 ต้องรวม profit center O* ด้วย

  • Manual adjustment 5 รายการถูกดึงจาก GL แทน flat file แล้ว (ลดงาน manual)
  • IBC = 3% กับ intercompany · 20% กับ non-intercompany — ตัดสินด้วย trading partner (VBUND)

ภาพรวม — รายงานนี้คำนวณอะไร

เครื่องมือคำนวณและประมาณการ “ภาษีเงินได้นิติบุคคลค้างจ่าย” รายเดือน

หลักการทางภาษี: กำไรทางบัญชี ≠ กำไรทางภาษี — ต้องปรับด้วย 2 ตระกูลรายการ

  • Permanent difference — ต่างถาวร ไม่กลับรายการ (เช่น ค่าปรับ · เงินบริจาคเกินเกณฑ์ · รายจ่ายต้องห้าม)
  • Temporary difference — ต่างชั่วคราว กลับรายการในอนาคต (เช่น ค่าเสื่อมบัญชี vs ค่าเสื่อมภาษี · ประมาณการหนี้สิน)
กำไรทางบัญชี
GL node ± Permanent diff ± Temporary diff − Allowances / LCF × Tax rate = ภาษีค้างจ่าย

3 delta ที่ต้องเข้าใจ “ทำไม” ไม่ใช่แค่ “อะไร”

ก) Valid From / Valid To — ทำไมต้องมี

รายงานภาษีต้องรันย้อนหลังได้ (ตรวจสอบ/แก้ไขแบบยื่นเก่า) ถ้า mapping หรือ layout เปลี่ยนกลางทาง การรันปีเก่าจะได้ผลลัพธ์ตาม config ปัจจุบัน = ผิด Valid From/To ทำให้โปรแกรม เลือก config ที่ใช้อยู่ ณ ปีที่รายงาน — FD ระบุว่า “Report should display same data as per the reporting year … with historical values and layout”

ข) GL account prefix A/B/C — เคล็ดลับ *999999999

ผังบัญชี S/4HANA ของ Client ขึ้นต้นด้วย A, B หรือ C (เช่น A999X042, B_PC07, C_PC34) ถ้า map ทีละตัวอักษรจะได้ 3 แถวต่อ 1 บัญชี → บวม FD จึงกำหนดให้ใช้ *999999999 — ดอกจันแทนตัวอักษรนำหน้า เพื่อ “รวมยอดของทั้ง 3 ตัวในแถวเดียว”

ตัวอย่าง: ต้องการยอดรวมของ A999X042 + B_PC07 + C_PC34 maintain ใน ZTAXA_T01 เป็น *999999999 (1 แถว แทน 3 แถว)

ค) RLDNR ใน upload table — ทำไมเพิ่งมามี

ECC มี ledger เดียวในบริบทนี้ แต่ S/4HANA มี หลาย ledger (0L, T1 …) รายการปรับปรุงที่อัปโหลดจึงต้องระบุว่า “ปรับที่ ledger ไหน” check table FINSC_LD_CMP คือ ตารางกำหนด ledger ต่อ company code → กันไม่ให้ใส่ ledger ที่บริษัทนั้นไม่มี

ผลกระทบข้ามระบบที่ FD เตือนไว้: การเปลี่ยนโครงสร้างตารางชุดนี้กระทบ (ก) Annual Tax Report (P2) และ (ข) Interface ส่งข้อมูลไป BI (ZTAXA_I01) → เวลาแก้ตารางต้องแจ้ง 2 ทีมนี้เสมอ · นี่คือเหตุผลที่ FD ลงตารางว่าตารางไหนถูกใช้โดยโปรแกรมใดบ้าง

  5. Operating cost/expenses ของ corporate profit center → ปันระหว่าง BOI/Non-BOI ตามสัดส่วนรายได้ในข้อ 1
  6. Expense adjustments → มาจาก flat file ตาม tax rate ที่ระบุในไฟล์
